# Employee Time Management System

A proof-of-concept QR-based attendance system for the Renewi Employee Time Management specification (Master Build Prompt v0.2). Employees hold a permanent opaque QR credential, a tablet browser scans it at the gate, the backend decides IN or OUT, and staff see a recorded on-site dashboard, attendance duration, exceptions, audited corrections and CSV exports. All data is synthetic. The application is a local proof of concept; it is not an approved real-data pilot, and nothing in this repository is a legal, DPIA or GDPR compliance statement.

## Stack

The backend is Python 3.12 with FastAPI, SQLAlchemy 2, psycopg 3 and Alembic on PostgreSQL 16. The frontend is Vite, React 18 and TypeScript with React Router, Dexie (IndexedDB) for the offline scan queue, `@zxing/browser` for camera decoding and `vite-plugin-pwa` for the scanner application shell. Browser verification uses Playwright with the Chromium build pre-installed under `/ms-playwright`. Everything runs locally; no platform container provisioning is used.

## Setup

Run the scripts with `bash` because the repository mount does not preserve execute bits. The local PostgreSQL cluster is stored outside the repository at `~/.etms-localdb` (override with `ETMS_LOCALDB`) and listens on port 5433 (override with `PGPORT`).

```bash
bash scripts/setup.sh          # backend venv, pip install, npm install, start cluster, generate backend/.env
bash scripts/reset_demo.sh     # drop and recreate etms_dev, migrate, seed the demo profile
```

`backend/.env` is generated by `scripts/gen_env.sh`, is never committed, and existing values are never overwritten. It contains the database URLs, a random `SECRET_KEY`, a generated `FERNET_KEY`, the attendance-policy settings and randomly generated `SEED_ADMIN_PASSWORD`, `SEED_SUPERVISOR_PASSWORD` and `SEED_HR_PASSWORD` values. There are no password literals in source or documentation: read the seeded passwords from `backend/.env` (never paste them into documents or tickets). `backend/.env.example` lists every variable with placeholders.

### Secure defaults

`APP_ENV` defaults to `production` and `COOKIE_SECURE` defaults to true except in `dev` and `test`. Outside those two environments the backend refuses to start with a weak or short `SECRET_KEY`, an invalid `FERNET_KEY`, an insecure session cookie or a wildcard `CORS_ORIGINS`. `scripts/gen_env.sh` writes `APP_ENV=dev` and `COOKIE_SECURE=false` for local synthetic use. The seed command only runs in `dev` or `test` and stops with a clear message when a seed password is missing. Logins are throttled (five failures lock the username for fifteen minutes by default and return HTTP 429 `login_locked` with `Retry-After`), every response carries security headers and an `X-Process-Time-Ms` header, and permissions are enforced on the server. The project does not terminate TLS itself; a deployment must provide HTTPS.

## Run

```bash
bash scripts/run_backend.sh    # FastAPI on :8000 (OpenAPI at /openapi.json, docs at /docs); run in the background
bash scripts/run_frontend.sh   # Vite dev server on :3000, proxying /api to :8000
```

Open `http://localhost:3000`. The Vite dev server is for development only. The offline application shell is a service worker that exists only in the production build, so offline reload must be exercised with:

```bash
cd frontend
npm run build
npm run preview                # production build on :4173 with the same /api proxy
npm run preview:https          # same, with a self-signed certificate for a tablet on the LAN
```

Stop the database with `bash scripts/db_stop.sh`.

### Camera and browser requirements

Browsers only grant camera access and register service workers in a secure context. `http://localhost` qualifies; a tablet opening a LAN IP address over plain HTTP does not, so use `npm run dev:https` or `npm run preview:https` (the certificate is self-signed and must be accepted on the tablet) or place the application behind HTTPS. The scanner was exercised only in headless Chromium (the revision installed under `/ms-playwright`) with a virtual camera. No other browser, no tablet and no physical camera has been tested.

## How it works, in short

The QR code carries a random opaque token and no personal data. The backend alone decides IN or OUT, under a row lock, at site level (not per gate). Duplicate scans inside the per-site duplicate window (default 120 seconds) and retried requests with the same client UUID never create a second event. A scan that fails validation creates no attendance event, discloses no employee identity and is listed in a staff-only scan log. A session still open after the per-site cut-off (default 06:00 on the next local day) stays on the dashboard as recorded IN and is flagged `missing_out`; no OUT is ever invented automatically. Overnight sessions are attributed to the local date of the IN. Hours are attendance duration (OUT minus IN), not paid working time. Corrections append a record with a mandatory reason and never overwrite the original event. All times are shown in the site time zone. The dashboard shows recorded attendance status, not verified presence.

### Offline approach and multiple tablets

The tablet stores every capture in IndexedDB before any network call, marks the capture mode (online or offline) at capture time and decides connectivity with a backend probe (`GET /api/scanner/ping`), not the browser online flag. Pending scans survive reloads and browser restarts and are sent in order, in chunks of at most 100, with the same client UUIDs. If an item fails with a retryable error the server stops the batch there, returns the later items as skipped, and the tablet keeps them pending and retries without losing or duplicating a scan. While offline the tablet shows only a tentative direction (or says the direction is decided on synchronisation); the server always decides, and a mismatch is surfaced after synchronisation. The server accepts an offline capture only between 48 hours in the past and one minute in the future. The design assumes one tablet per site. Several tablets that are independently offline cannot know each other's scans, so their tentative directions may be wrong until synchronisation; this limitation is documented rather than hidden and needs a Renewi decision (RC-04).

## Known limitations

Physical camera decoding, tablet fullscreen and wake lock, a physical tablet or browser restart, lighting conditions, opening the CSV in Excel with a Dutch locale, LibreOffice conversion, PDF badge decoding with `pdftoppm`, keyboard-only navigation and touch-target size inspection were not run; they need a person with the device or tool, as listed in `docs/TEST_RESULTS.md`. Browser evidence is headless Chromium against the production preview with a virtual camera. Offline captures live in browser storage, so clearing site data on the tablet loses unsynchronised scans. The tablet clock is trusted inside the 48-hour offline window. The scanner shell works offline only in the production build over `localhost` or HTTPS. The duplicate window, missing-OUT cut-off, overnight attribution, site-level IN/OUT interpretation, single-tablet assumption, correction approval flow and role permissions are configurable engineering defaults awaiting Renewi confirmation (RC-01 to RC-05). A scan after the cut-off closes the stale session and the session is flagged `out_after_cutoff` (RC-08). No Renewi brand assets exist in the workspace, so the interface is neutral text-only. The frontend index chunk exceeds 500 kB after minification (non-blocking build warning). Data processing agreement, works council, DPIA, lawful basis, retention periods and approved EU hosting are Renewi pilot gates and are not addressed by this software.
